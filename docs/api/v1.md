# AI Proctor API v1

Read your organization's people, projects, timesheets, time, check-in metadata, reports,
alerts and time off, and create clients, projects, tasks and manual entries, from payroll, BI
and HR tools. [Webhooks](#webhooks) push events to your endpoints as they happen.

- **Reference:** [`openapi.json`](openapi.json) (OpenAPI 3.1), also served at
  `GET /v1/openapi.json`. Generated from `supabase/functions/api-v1/routes.ts` with
  `pnpm api:openapi`.
- **Base URL:** until the production `/api` host is set up at deploy (M6), the API is served
  by the `api-v1` Edge Function: `<backend URL>/functions/v1/api-v1/v1/...` (locally
  `http://127.0.0.1:54321/functions/v1/api-v1/v1/people`).

## Keys

An owner or admin makes a key on the dashboard: **Settings → API → New API key**. Each key has
a name, the scopes it may use, and an optional expiry. The key (`aip_` and 43 characters) is
shown once; only its SHA-256 is stored. Send it as a bearer token:

```sh
curl -H "Authorization: Bearer aip_..." "$BASE/v1/people?active=true"
```

A key sees the whole organization and acts as the person who made it. It stops working when it
is revoked, when it expires, or when that person is no longer an active owner or admin.

| Scope | Allows |
| --- | --- |
| `people:read` | `GET /v1/people` |
| `teams:read` | `GET /v1/teams` |
| `projects:read` | `GET /v1/clients`, `/v1/projects`, `/v1/tasks` |
| `projects:write` | `POST /v1/clients`, `/v1/projects`, `/v1/tasks`, and `POST .../{id}/archive` on each |
| `shifts:read` | `GET /v1/shifts` |
| `timesheets:read` | `GET /v1/timesheets` (status, approver, week totals) |
| `time:read` | `GET /v1/segments`, `GET /v1/manual-entries` |
| `time:write` | `POST /v1/manual-entries` |
| `checkins:read` | `GET /v1/checkins` (metadata only) |
| `reports:read` | `GET /v1/reports/people`, `GET /v1/reports/tasks` |
| `alerts:read` | `GET /v1/alerts` |
| `timeoff:read` | `GET /v1/time-off` (requests: type, paid, days or times, status, approver; never the notes), `GET /v1/holidays` |

## Conventions

- **JSON** in and out. Lists return `{ "data": [...], "next_cursor": "..." | null }`; a write
  returns `{ "data": {...} }` (201 for a create).
- **Times** are ISO 8601 with a zone (`2026-11-05T13:00:00+00:00`). Times you send must carry
  a zone (`Z` or an offset). Days (`from`, `to`) are `YYYY-MM-DD`, in each person's own time
  zone where it matters.
- **Durations** are seconds, exact: never rounded (`duration_s`, `worked_s`, ...).
- **Paging:** `limit` (1 to 500, default 100) and `cursor` (the previous page's
  `next_cursor`, with the same other parameters). Lists are ordered by `updated_at`, then
  `id`.
- **Syncing:** `updated_since=<time>` returns what changed at or after that time. Pass the
  newest `updated_at` you have, minus a few minutes, and upsert by `id`. Segments are rebuilt
  per person-day and shifts are replaced per person: replace those wholesale for what you
  receive. Deleted data (retention, deletion requests) simply disappears; reconcile with a
  full listing now and then.
- **Unknown parameters are refused** (400), so a typo never silently widens a query.
- **Rate limit:** 120 requests a minute per key. Every response carries `X-RateLimit-Limit`,
  `X-RateLimit-Remaining` and `X-RateLimit-Reset` (epoch seconds); over the limit you get 429
  with `Retry-After`.

## Errors

```json
{ "error": { "code": "invalid_param", "message": "limit: expected a whole number from 1 to 500", "param": "limit" } }
```

| Status | Codes |
| --- | --- |
| 400 | `invalid_param` (with `param`), `invalid_json`, and the rules' own (`invalid_range`, `range_too_long`, `in_the_future`, `project_not_allowed`, `task_not_allowed`, `user_inactive`, `too_many_people`, ...) |
| 401 | `missing_key`, `invalid_key`, `key_revoked`, `key_expired`, `key_creator_inactive` |
| 403 | `insufficient_scope` |
| 404 | `not_found`, `client_not_found`, `project_not_found`, `task_not_found`, `user_not_found` |
| 405 | `method_not_allowed` |
| 409 | `name_taken`, `overlaps_manual_entry`, `overlaps_clocked_time`, `day_locked` |
| 429 | `rate_limited` |

`code` is stable; `message` is for people and may change.

## Writes

- **Clients, projects, tasks:** created and archived with the same rules as the dashboard's
  Projects page (names unique per org, 1 to 120 characters). Archiving twice changes nothing.
  A new project has no members; add them on the dashboard.
- **Manual entries** (`POST /v1/manual-entries`) follow the person's own request rules
  (TS-07..09, TS-24): pending until their manager decides (approved at once when they need no
  approval), at most 24 hours, not in the future, a project they are a member of, no overlap
  with clocked time or their other entries, nothing in an approved week. The key's creator is
  the actor in the audit log.

## What the API never returns

Capture images or links to them, window titles, browser domains, the notes on time-off requests
and their decisions, when a check-in was or will be
scheduled (so never the next check-in), anti-cheat flag details on check-ins, private pause
reasons, and people's own words about a missed check-in. Check-ins are metadata only: the
outcome, when it was shown and answered, and the response time.

## Audit

Making and revoking a key are audit-logged (`api_key.created`, `api_key.revoked`). Every request
is logged too, as its key's creator: a read as `api.read` with the key, the operation, the
filters and the row count (like an export), a write as `api.write`. They show on the
dashboard's Audit log page.

## Webhooks

An owner or admin adds an endpoint on **Settings → API → Webhooks**: an `https://` URL on a
public host (no private, loopback or link-local addresses, no user name or password) and the
events it wants. The endpoint's **signing secret** (`whsec_` and 43 characters) is shown once,
when it is added or rotated. An organization can have up to 10 endpoints. Adding, changing,
deleting and rotating are audit-logged (`webhook.created`, `webhook.changed`,
`webhook.deleted`, `webhook.secret_rotated`).

| Event | When | `data` |
| --- | --- | --- |
| `timesheet.submitted` | A week is submitted, or reopened after approval (`previous_status` is `approved`) | `Timesheet` plus `previous_status` |
| `timesheet.approved` | A week is approved, including one approved on submit (no approval needed) | `Timesheet` plus `previous_status` |
| `timesheet.returned` | A week is returned to the person | `Timesheet` plus `previous_status` |
| `alert.raised` | A manager alert is raised about a person (once, however many recipients) | `{ user_id, kind, details, triggered_at }` |
| `person.invited` | A person is added (invited or imported) | `Person` |
| `person.deactivated` | A person is deactivated | `Person` |
| `time_off.decided` | A time-off request is approved or declined (or approved on asking, for someone with no manager) | `TimeOff` |

The shapes are the API's own (see `webhooks` in [`openapi.json`](openapi.json)). Each event is a
`POST` with a JSON body:

```json
{ "id": "6f1c…", "type": "timesheet.approved", "created_at": "2026-11-05T18:02:11.52+00:00",
  "api_version": "v1", "data": { "id": "…", "user_id": "…", "status": "approved", … } }
```

and these headers:

| Header | |
| --- | --- |
| `X-AIProctor-Event` | The event type |
| `X-AIProctor-Event-Id` | The event's `id`: the same in every retry, so dedupe on it |
| `X-AIProctor-Delivery` | This endpoint's delivery of the event |
| `X-AIProctor-Timestamp` | Unix seconds when this attempt was signed |
| `X-AIProctor-Signature` | `v1=` and the hex HMAC-SHA256 of `<timestamp>.<raw body>` with the signing secret |

**Verify every request** before you trust it: compute the HMAC over the timestamp, a dot and the
raw body exactly as received (before any JSON parsing), compare it in constant time, and refuse
timestamps more than 5 minutes old so a captured request can't be replayed.

```js
import { createHmac, timingSafeEqual } from "node:crypto";

// rawBody: the request body as received (a string or Buffer), not re-serialized JSON.
export function verifyAiProctorWebhook(rawBody, headers, secret) {
  const timestamp = headers["x-aiproctor-timestamp"];
  const signature = headers["x-aiproctor-signature"] ?? "";
  if (!timestamp || Math.abs(Date.now() / 1000 - Number(timestamp)) > 300) return false;
  const expected = `v1=${createHmac("sha256", secret).update(`${timestamp}.${rawBody}`).digest("hex")}`;
  const a = Buffer.from(signature);
  const b = Buffer.from(expected);
  return a.length === b.length && timingSafeEqual(a, b);
}
```

```python
import hashlib, hmac, time

def verify_aiproctor_webhook(raw_body: bytes, headers, secret: str) -> bool:
    timestamp = headers.get("X-AIProctor-Timestamp", "")
    signature = headers.get("X-AIProctor-Signature", "")
    if not timestamp.isdigit() or abs(time.time() - int(timestamp)) > 300:
        return False
    mac = hmac.new(secret.encode(), timestamp.encode() + b"." + raw_body, hashlib.sha256)
    return hmac.compare_digest(signature, "v1=" + mac.hexdigest())
```

**Delivery.** Answer with any 2xx within 10 seconds. Anything else (another status, a redirect,
which is not followed, a timeout, no connection) is retried after 1, 4, 16, 64, 256 and 1024
minutes: 7 attempts over about 23 hours, after which the delivery has failed. Events can arrive
more than once and out of order: dedupe on the event id and use `updated_at` in `data`. When 5
deliveries in a row have failed, the endpoint is turned off and every owner and admin is
notified; turn it back on from the same page once the receiver works. Rotating the secret takes
effect at once: deliveries your receiver refuses while you update it are retried.

**Delivery log.** The page lists each delivery with its status, attempts, the receiver's HTTP
status and the next retry. Deliveries are kept 30 days.

**Deleted people.** When a person's data is deleted (ADM-05), their delivered events leave the
log, and events about them still waiting to go out are sent with `data` reduced to ids and
`"redacted": true`.
